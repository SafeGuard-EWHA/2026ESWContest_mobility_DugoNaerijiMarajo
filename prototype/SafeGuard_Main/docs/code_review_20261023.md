# SafeGuard 0.1.0 재검토 및 0.1.1 수정 기록

검토일: 2026-10-23. 대상은 전달한 `SafeGuard_Main.zip` 0.1.0의 실제 파일이다. 검토 시작 시 압축파일의 모든 항목이 작업 소스와 같은지 바이트 단위로 확인했다.

## 판단

단일 C++ FSM, Python 센서 연결부, 입력 유효시간, 정상 OR/장애 AND, 보호 유지, DEMO와 REAL 구분이라는 구조는 설계 방향에 맞는다. 그러나 기존 테스트가 다 통과하더라도 실제 재시작과 센서 처리 활성화의 상호작용을 충분히 검증하지 못했다. 0.1.0을 오류 없는 완성품이라고 판단할 수 없으며, 아래 재현한 결함을 수정한 0.1.1을 제공한다.

## 재현한 결함과 수정

| 우선순위 | 결함과 발생 조건 | 0.1.1 조치 |
|---|---|---|
| 높음 | 이전 메인에서 보호 출력이 ON인 채 메인을 다시 시작하면 INIT의 초기 OFF가 기존 보호를 해제할 수 있음 | MCU의 현재 상태와 제어 세션을 먼저 확인. 기존 ON을 보호 요구로 복원하며 유효한 복귀와 수동 해제 조건 유지 |
| 높음 | ON 명령 ACK 후 MCU가 재부팅·연결 중단되어도 예전 ACK를 유지하며 같은 출력 요구를 재전송하지 않음 | 상태 만료 시 ACK 무효화. 부팅·세션·출력 상태를 동기화한 뒤 현재 요구를 새 ID로 재전송 |
| 높음 | 500ms 보고 사이에 ESTOP을 짧게 눌렀다 놓으면 MCU만 정지를 기억하고 메인은 놓침 | 현재 스위치와 `estop_latched`를 별도로 전달. 실제 구동 모드 메인은 잠금을 복원하며, 해제된 스위치와 승인된 수동 재무장 ACK로 해제 |
| 중간 | 카메라/mmWave를 필수로 설정하면 INIT에서 데이터를 기다리면서 처리를 꺼 두어 시작할 수 없음 | 초기화와 초기화 실패 복구 중 필수 센서 처리를 켜고 데이터 준비를 확인 |
| 중간 | THERMAL/PROTECTION에서 의도적으로 처리를 멈춘 카메라/mmWave를 고장으로 표시 | 처리 활성 상태와 시작 유예시간을 적용. 실제 활성 센서의 수신 만료 경고 유지 |
| 중간 | ESP32가 새로 부팅되어 PIR=false를 보내도 이전 부팅의 최근 PIR=true가 남아 장애 AND 판정에 쓰일 수 있음 | 부팅 변경 시 양성 기록 초기화. uptime 역행도 무효 처리 |
| 중간 | 원시 ESP 입력에 source=DEMO가 있어도 연결부가 REAL_ESP32로 바꾸고 유효 센서로 전달 | 명시적인 출처·모드 충돌 거부. ACK도 요청 당시 부팅과 현재 부팅에 결합 |
| 낮음 | 유효한 열 예측이 시간 범위 내 위험 온도에 도달하지 않으면 WAITING으로 표시. 변경된 위험 기준이 그래프에 반영되지 않음 | ‘예측 범위 내 미도달’ 표시. 제목·그래프 기준선에 실제 설정 온도 사용 |

## 검증

- Linux x86_64 / GCC 13.3 / C++17 / Release, `-Wall -Wextra -Wpedantic -Werror` 빌드.
- CTest의 Core 및 입력·제어 통신 테스트 2묶음. Release에서도 검증문이 활성화되어 있다.
- Python 센서 연결부 테스트 22개. 출처 충돌·부팅 구분·컨트롤러 상태 누락·잘못된 ACK 회귀 검사 포함.
- 기존 전체 프로세스 시나리오 7개: 정상, mmWave 장애, UNKNOWN, 외기 장애, ESTOP, 센서 없는 REAL 및 하드웨어 DEMO.
- Linux 가상 직렬 포트(PTY)로 실제 C++ 메인과 Python hub를 함께 실행. 이전 ON과 3초 세션 인계 지연, MCU 재부팅, 수신 중단·복구, 이미 놓은 ESTOP과 수동 재무장을 검사. 이 상대 장치는 소프트웨어 모형이다.
- 대시보드 HTTP 제어 시험 및 실제 화면 스크립트의 DOM 회귀 검사. 브라우저 시각 검증은 수행하지 않았다.
- ESP32 참고 스케치는 ArduinoJson 6.21.5/7.4.2의 실제 헤더와 GPIO/UART/시간 모형으로 기본·출력 활성 변형 4개를 검사. ESP32 대상 컴파일이나 업로드는 아니다.
- 기존 UWB reader v1.1.0의 바이트를 보존했다.

검사별 최종 결과는 `software_validation.json`에 기록한다. 이 기록은 센서 검출률·거리 정확도·팬 실동작·전력 절감 실측 증거가 아니다.

## 남은 구현과 실물 확인

1. A 담당 실제 코드·핀 배선·팬/부저와 위 통신 계약을 연결해야 한다. 실제 구동을 켜려면 새 상태 필드가 필요하며 없을 때는 WAITING_CONTROLLER로 남는다.
2. B의 선택된 TI 펌웨어/설정에 맞는 원시 UART 파서와 검출 검증이 필요하다. 이 패키지의 mmWave 포트는 이미 정규화한 B 출력용이다.
3. REAL 외기 API와 실측 R/C/Q 보정을 연결해야 한다. 현재 REAL 예측은 기본 비활성이다.
4. 이번 전체 메인을 실제 Pi·A/B 센서·구동부로 실행한 통합 검증은 아직 하지 않았다. 이미 성공한 독립 C블록의 실물 결과와 구분한다.

이 검토는 발견한 결함의 수정과 위 조건의 검증을 의미한다. 모든 가능한 고장 조건이나 완성된 실차 안전성을 보장하는 검증은 아니다.
