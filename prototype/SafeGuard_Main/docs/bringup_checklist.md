# 순서대로 연결하는 체크표

이미 성공한 C블록 거리 측정·MA7·단절/복구를 처음부터 반복하는 목록이 아닙니다. 새 메인을 실행하고 아직 없는 A/B 연결을 채우는 순서입니다.

## 1단계 — 새 프로그램 설치와 가상 흐름

- [ ] ZIP을 `~/SafeGuard_Main`에 풀고 기존 `~/safeguard_c`는 보존한다.
- [ ] `bash scripts/install_pi.sh`, `bash scripts/build.sh`를 실행한다.
- [ ] `bash scripts/run_demo.sh`의 표시가 SOFTWARE SIMULATION인지 확인한다.
- [ ] 브라우저에서 입력 출처·FSM·온도·출력 요청을 볼 수 있다.
- [ ] 종료 후 `runs/`에 해당 실행의 기록이 남는다.

이 단계의 산출물은 실행 가능한 메인과 가상 논리 흐름입니다. 실물 센서 전체 검증 결과는 아닙니다.

## 2단계 — 성공한 실제 C 입력을 새 메인에 연결

- [ ] 이전 UWB reader를 종료해 USB 포트를 한 프로그램만 사용한다.
- [ ] 차량측 USB·Pi 전원을 유지하고 `bash scripts/run_real.sh`를 실행한다.
- [ ] 실제 peer `0CA7`의 값과 데이터 출처가 나타난다.
- [ ] 미연결 A/B가 무효로 표시되고, 가짜 감지·ACK로 채워지지 않는다.
- [ ] DRY_RUN임을 확인한다.

전원 재연결 때문에 `lec`가 꺼진 경우만 README의 miniterm 절차를 사용한다. 역할 재설정·펌웨어 재설치·거리 보정을 다시 시작하지 않는다.

## 3단계 — A의 실제 데이터와 구동 계약 연결

필요 자료: 현재 `.ino`/ESP32 코드, 실제 핀표와 배선 사진, 센서 출력 한 줄, 명령/ACK 한 줄.

- [ ] PIR과 SHT31의 값·유효성·시각이 계약과 맞는다.
- [ ] 비상정지 감시 입력의 의미와 유효성이 확인됐다. 없는 감시 입력을 항상 false로 정상 처리하지 않는다.
- [ ] `hardware.esp32_port`를 장치에 맞추고 DRY_RUN으로 실제 센서값부터 받는다.
- [ ] A의 12V/로직 분기·구동단 정격·물리 비상정지 검수가 끝났다.
- [ ] 구동 허용 조건과 `actuation.enabled`를 팀이 확인한 뒤 실제 명령/ACK를 연결한다.
- [ ] 같은 명령 ID의 재수신, timeout, 통신 끊김에서 합의한 동작을 보인다.

참고 펌웨어는 실제 보드·배선과 대조한 뒤 적용한다. Pi 프로그램을 종료하는 것으로 실제 보호 출력이 자동 해제된다고 가정하지 않는다. 물리 비상정지와 통신 상실 정책은 별도다.

## 4단계 — B의 카메라·mmWave 의미 있는 출력 연결

필요 자료: TI 보드 리비전, 정확한 펌웨어/데모 버전, `.cfg`, 원시 UART 로그와 기존 파서.

- [ ] 카메라 motion의 ROI·연속 프레임 조건과 조명 변화 반응을 확인한다.
- [ ] 카메라 분석을 사용할 때 `--camera` 설치와 `camera_enabled` 설정을 적용한다.
- [ ] TI 바이너리 UART는 해당 펌웨어에 맞는 파서로 해석한다. `mmwave_json_port`는 정규화된 JSON 생산자용이다.
- [ ] mmWave의 정상 통신, 정상 미검출, 의미 있는 presence, 장치 장애가 구분된다.
- [ ] `mmwave_validated`는 실제 판정 조건 검증 후에만 true로 한다.

본선 핵심은 presence/미세 움직임이다. 호흡 검출은 안정성이 확인된 추가 결과로 다룬다. 임의 물체의 점 구름이나 UART 수신을 탑승자 확정으로 치환하지 않는다.

## 5단계 — 온도와 하드웨어 DEMO

- [ ] `bash scripts/run_demo.sh --hardware`에서 감지 입력은 실제, 온도는 DEMO 프리셋으로 구분된다.
- [ ] 화면에서 실측 온도와 선택한 판단용 온도의 출처를 구분한다. 실측이 없으면 빈값/무효가 보인다.
- [ ] REAL 모델은 기존 열 모델/보정 로그와 실제 외기 입력을 연결한 후 활성화한다.
- [ ] 현재 온도 >=35°C의 반응과 예측에 의한 선제 반응을 구분한다.
- [ ] 실제 감지 → 판단 → Fan/Buzzer 명령 → ACK → 실제 회전·소리를 한 흐름으로 확인한다.

자료가 없는 동안에는 가상 시나리오로 논리를 검증하고 REAL 예측을 꺼 둔다. R/C/Q 후보값을 실측으로 설명하지 않는다.

## 6단계 — 전체 동작의 완료 증거

현재 C에서 이미 확인한 시험을 반복하기 위한 단계가 아니라, A/B를 연결한 전체 상태기계의 마지막 확인이다.

- [ ] 정상 OR 네 조합과 장애 AND 조건이 실제 입력 의미와 일치한다.
- [ ] UNKNOWN과 센서 무효가 ‘탑승자 없음’으로 표시되지 않는다.
- [ ] 보호 중 일시적인 미검출·통신 장애로 보호 요청이 사라지지 않는다.
- [ ] 복귀와 수동 해제 조건, 비상정지와 재무장 조건을 각각 확인한다.
- [ ] 로그의 요청/ACK와 실제 동작 증거를 구분해 남긴다.
- [ ] 센서 검출 시험과 가열 시험은 분리하고, 보호 출력은 모형/무인 시험체에서 확인한다.
- [ ] 성능 측정은 REAL/DEMO/REPLAY를 나누고 실패·결측도 기록한다.
- [ ] 전력은 Pi USB·12V 구동·보호자 전원의 측정 경계와 시간을 맞춰 계산한다. 상태표의 추정 전력을 실측 에너지로 쓰지 않는다.

이 단계까지 확인하기 전에는 ‘코드 구현’, ‘가상 논리 검증’, ‘개별 하드웨어 확인’, ‘전체 실물 통합’을 구분해 보고한다.
