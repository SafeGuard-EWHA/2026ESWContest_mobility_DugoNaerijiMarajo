작성: 2026-10-24, 실제 코드와 실제 시험 기록 기준. **시험하지 않은 것은 "미확인", 정하지 않은 것은 "협의 필요"로 적었다.**
코드 저장소: https://github.com/yoontf0/safeguard-mmwave-simulator (Pi 클론 경로 `/home/pi/safeguard-mmwave-simulator`)

## 0. 먼저 알아야 할 것 (충돌 가능성 큼)

1. **레이더 보드에 지금 구워진 펌웨어는 Vital Signs**다. 메인 쪽에서 확인한 "Platform xWR68xx, SDK 03.06.02.00" 응답은
   그 전에 구워져 있던 **Out-of-Box 데모** 기준이다. 펌웨어 변경 이력:
   | 시각 | 펌웨어 |
   |---|---|
   | 10/23 18:42 | mmWave SDK 3.6.2 Out-of-Box (`xwr68xx_mmw_demo.bin`) ← 메인이 시험한 상태 |
   | 10/23 22:23 | Radar Toolbox 4.00 **3D People Tracking** (`3D_people_track_6843_demo.bin`) |
   | 10/24 02:30경 | Radar Toolbox 4.00 **Vital Signs With People Tracking** (`vital_signs_tracking_6843ISK_demo.bin`) ← **현재** |
   (메인 시험의 "10초에 패킷 100개" = 10 프레임/초는 Out-of-Box cfg의 프레임 주기 100 ms와 맞는다.
   People Tracking은 18 프레임/초, Vital Signs는 11 프레임/초였다. 메인 시험 시각은 블록 B가 모르므로 이 판단은 추정이다.)
   → 지금 상태로 `xwr68xx_ods_oob_20261023.cfg`를 보내면 동작이 보장되지 않는다. **메인에서 쓸 펌웨어를 정해서 다시 구워야 한다.**
   블록 B 추천은 **3D People Tracking** (근거는 4절). 굽기는 노트북 UniFlash로 한다 (Pi에서 굽는 방법은 미확인).
2. **한 번 `sensorStop`한 뒤 다시 cfg를 보내면 `sensorStart`가 응답하지 않았다** (People Tracking, Vital Signs에서 여러 번 재현).
   **USB를 뺐다 꽂아 전원을 껐다 켜야** 다시 시작된다. "필요할 때만 켰다 끄기"는 지금 방식으로는 안 된다 (5절).
3. 시리얼 포트는 **한 프로그램만** 열 수 있다. 메인의 레이더 시험 스크립트와 블록 B의 `mmwave_reader.py`를 동시에 실행하면 안 된다.

## 2. 실행 코드

| 파일 | 하는 일 | 상태 |
|---|---|---|
| `hardware/mmwave/mmwave_reader.py` | cfg 전송 → 데이터 포트 수신 → 매직워드로 프레임 분리 → TLV 해석 → 1초 요약 출력 + 프레임별 CSV | Pi·노트북 실측 |
| `hardware/camera/camera_motion.py` | Pi 카메라 프레임 차분 움직임 검출 | Pi 실측 2회 |

- 실행 중인 코드와 개발 중인 코드가 따로 있지 않다. 저장소 `main`이 최신이다 (Pi 클론은 `git pull` 필요할 수 있음).
- 메인 폴더(`/home/pi/SafeGuard_Main`)는 **건드리지 않았다.**
- 라이브러리: `python3-serial` 3.5 (Pi에 기본 설치되어 있었음), 카메라는 `python3-picamera2` 0.3.38 + numpy. OpenCV 안 씀.

`mmwave_reader.py`가 해석하는 TLV (형식은 Radar Toolbox 4.00 Industrial Visualizer 파서와 같게 맞춤):

| 펌웨어 | TLV | 내용 |
|---|---|---|
| Out-of-Box | 1 | 점 구름 x, y, z, 도플러 |
| People Tracking | 1020 / 1010 / 1021 | 압축 점 구름 / **추적 대상**(id, x, y, z) / **재실 여부**(0·1) |
| Vital Signs | 1040 | 호흡수, 심박수, 호흡 흔들림, 거리 칸 |

실행 (Pi):
```bash
cd ~/safeguard-mmwave-simulator
# 포트는 CP2105 by-id로 자동 탐색. 오래 돌릴 땐 nohup + -u
nohup python3 -u hardware/mmwave/mmwave_reader.py --cfg hardware/mmwave/people_tracking/ODS_sedan_est.cfg \
  --duration 300 --csv ~/radar.csv > ~/radar.log 2>&1 &
tail -f ~/radar.log
```
```bash
python3 -u hardware/camera/camera_motion.py --duration 120 --csv ~/cam.csv --snap-dir ~/cam_snaps
```

## 4. 점유 판단 방식과 검증 범위

**코드에 점유 판단 로직은 없다.** 리더는 TI 펌웨어가 낸 `num_tracks`·`presence`를 그대로 기록·출력할 뿐이다.
즉 "레이더가 사람 있음/없음을 판단해 메인에 넘기는 기능"은 **미구현**이다.

대신 판단 규칙을 정하기 위한 **실측 시험**은 했다 (Pi, 과방, 센서 약 1.2 m 높이·살짝 아래, 의자 1.5 m 앞, 각 5분, 18 프레임/초, 누락 0):

| 시험 | cfg | 사람 | 정지 구간 결과 | 나간 뒤 |
|---|---|---|---|---|
| A | TI 원본 (방 8 m) | 3명 | 3명 70.4%, 2명 29.4%, **0명 0%** | 0명 |
| B | **`ODS_sedan_est.cfg`** | 1명 | **1명 95.7%**, 0명 4.3%. **추적·재실 둘 다 0인 프레임 1.3%, 최대 공백 1.3초** | **약 6초 뒤 0** |
| C | TI 원본 (방 8 m) | 1명 | 정확히 1명 **0%** (유령 2~5개, 약 4 m 앞 벽 반사) | **약 33초** 유령 남음 |

- **가만히 있는 사람: 시험했다** (위 A·B·C, 정지 구간 약 2분 45초). 펌웨어의 미세 움직임(fineMotion) 모드가 켜져 있다.
- 시험 B 기준으로 블록 B가 **제안하는** 규칙 (구현 안 함, 협의 필요):
  `num_tracks > 0 또는 presence == 1`이면 "있음", **5초 연속** 둘 다 0일 때만 "없음". (시험 B의 최대 공백 1.3초를 덮음)
- 검출점 0개를 곧바로 "사람 없음"으로 처리하면 안 된다. 정지한 사람이 있어도 점 0개 프레임이 흔하다 (3-2 예시 참고).
- 호흡·심박 (Vital Signs): 거리 0.95 m 고정·안정 호흡에서 1분 중앙값 호흡수 오차 0.4~1.4회/분 (2구간). 빠른 호흡(22~25회/분)에서는 -40~47%.
  심박은 정답 미측정. **멘토 의견대로 점유 판단에는 쓰지 않고 정확도도 주장하지 않는다.**
- 카메라: 손 움직임은 바로 잡지만 **40초 정지 착석은 계속 "정지"** (카메라로는 정지한 사람을 못 잡는다는 실측).

## 5. 설치 방향과 센서 제어

- 시험 배치: 선반 위 약 1.2 m, 안테나 면이 의자를 향하게 살짝 아래로, 의자 1.5 m 앞. **배치 사진은 아직 없다** (찍어서 추가 필요).
- 좌표: People Tracking 펌웨어가 cfg의 `sensorPosition`(높이, 기울기)과 `boundaryBox`/`staticBoundaryBox`/`presenceBoundaryBox`(바닥 기준 X 좌우, Y 앞쪽 거리, Z 높이, m)로
  **장치 안에서** 좌표를 바꾸고 영역을 거른다. 리더는 추적 좌표를 바꾸지 않고 그대로 쓴다.
  차량용 cfg의 숫자는 **실측이 아닌 추정**이고, 실차·전동차에서 맞는지 **미확인**.
- 시야: 좌우·위아래 ±70°. **보드 바로 뒤나 옆뒤에 있어도 잡힌 적이 있다** (대각선 뒤로 멀리 가야 0명). 실차에서 앞좌석·창밖 사람 확인 필요.
- 켜기/끄기:
  - 리더는 시작할 때 cfg(마지막 줄 `sensorStart`)를 보내고, 끝날 때 `sensorStop`을 보낸다.
  - **멈춘 뒤 다시 시작하려면 USB 전원을 껐다 켜야 했다** (0절 2번). 소프트웨어만으로 껐다 켜기는 **미확인/현재 불가**.
    대안은 협의 필요: (1) 레이더는 계속 켜 두고 메인이 필요할 때만 결과를 읽기, (2) USB 전원 스위칭 (미시험).
- 시작 후 첫 결과: 프레임은 `sensorStart` 직후 1초 안에 들어왔다. cfg 전송 시간은 따로 재지 않았다 (수 초).
  사람이 앉은 뒤 추적이 생길 때까지 시험 B에서 약 1초 안팎. Vital Signs 호흡 값은 수십 초 지나야 안정.
- 실행 조건: 같은 포트를 두 프로그램이 동시에 열면 안 됨, 레이더 USB를 뺐다 꽂은 뒤 실행, Windows Visualizer는 노트북에서 데이터가 7~8% 깨지므로 시연에 쓰지 않음.
- `safeguard-navigation.service`, 네트워크, 메인 폴더는 **건드리지 않았다.** 블록 B 시험에 재부팅은 필요 없었다.

## 메인 담당에게 받아야 할 것

1. **Python → C++ 메인 입력 형식**: `sensor_hub.py`(또는 해당 파일)와 입력 파서. 레이더·카메라 결과를 어떤 필드·형식으로 넘겨야 하는지 맞추기 위해.
2. **`configs/real_navigation.json`** 등 메인 설정 파일: 센서 포트·주기 설정이 있는지 확인하기 위해.
3. 메인이 레이더를 시험한 **스크립트**: 73,345바이트·100패킷 시험에 쓴 코드. 포트를 고정(`/dev/ttyUSB0/1`)으로 여는지, 리더와 역할이 겹치는지 확인하기 위해.
4. 메인이 쓰는 **카메라 코드** (`MOTION/NO_MOTION` 출력): 블록 B `camera_motion.py`와 무엇을 남길지 정하기 위해.
5. 레이더 결과에 바라는 **갱신 주기와 지연 한계**, 레이더를 **계속 켜 둬도 되는지** (전원·발열).

## 충돌 가능성

| 항목 | 내용 | 제안 |
|---|---|---|
| 펌웨어 | 메인 시험은 Out-of-Box, 보드는 지금 Vital Signs | 쓸 펌웨어를 정해 다시 굽기 (블록 B 추천: People Tracking) |
| 포트 번호 | ESP32(USB-시리얼)도 `/dev/ttyUSB*`로 잡힐 수 있다. 리더는 CP2105 by-id를 먼저 쓰지만, 못 찾으면 `/dev/ttyUSB0/1`로 넘어간다 | by-id 경로나 udev 고정 이름 사용, 리더의 `/dev/ttyUSB0/1` 대체 동작은 없애는 것을 검토 |
| 포트 독점 | 메인 레이더 스크립트와 리더를 동시에 실행 불가 | 레이더 포트를 여는 프로그램을 하나로 정하기 |
| 다시 시작 | `sensorStop` 뒤 USB 재연결 없이는 재시작 실패 | 계속 켜 두기 또는 전원 스위칭 협의 |
| 카메라 코드 2개 | 메인 쪽 `MOTION/NO_MOTION` 코드와 블록 B `camera_motion.py` | 하나로 정하기 |
| 출력 형식 | 리더는 한국어 텍스트 + CSV, JSON 아님 | 메인 형식을 받아 맞추기 |
| CPU·발열 | 레이더+카메라+UWB+메인 동시 실행은 **미시험** | 통합 리허설 때 `vcgencmd get_throttled` 확인 |
